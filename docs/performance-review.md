# 캘린더 리사이즈 성능 조사

조사·최적화 측정일: 2026-10-29. 최종 정리: 2026-11-01. 아래 기존 구조 분석은 최적화 전 소스를 기준으로 하며, 리사이즈 병목에 대한 코드 수정과 회귀 검증을 완료했다.

## 적용 결과

- `Calendar.Rendering.cs`로 화면 구성 경로를 분리했다. 날짜·요일·주별 Grid는 표시 범위/요일 헤더 템플릿이 바뀔 때 구성하고, 리사이즈 중에는 유지한다.
- 가로 크기 변경은 기존 Star 열이 처리한다. 높이는 표시 가능한 이벤트 줄 수가 달라질 때만 별도 갱신한다.
- 표시 용량이 바뀌면 기존 이벤트·더보기 버튼과 행 정의를 재사용한다. 새로 나타나는 조각만 만들고 사라진 조각만 제거한다. 입력 핸들러는 재사용되는 최신 컨텍스트를 읽는다.
- 이벤트별 리소스 사전 생성과 Source 지정을 제거했다. 공통 ThemeResource에서 호버·누름 색을 제공한다. 테마 전환 시 구분선 브러시만 갱신한다.
- 날짜 선택은 이전/새 날짜의 알림 가능한 컨텍스트와 선택선만 갱신한다. 이벤트 선택도 이전/새 이벤트의 조각만 갱신하며, 키보드 Tab 대상 변경은 두 날짜에 한정한다.
- 월간 그리드와 공개 범위 조회를 캐시했다. 월간 구현 세부 사항은 WinUI 월간 렌더러에 두고 공통 코어 계약은 변경하지 않았다.

동일한 Release JIT 조건과 90회 크기 변경 요청을 사용한 전후 측정:

| 시나리오 | 자체 화면 갱신 호출 전 → 후 | 날짜 버튼 생성 전 → 후 | 갱신 중앙값 전 → 후 |
| --- | ---: | ---: | ---: |
| 가로만 변경 | 54 → **0** | 1,890 → **0** | 24.81ms → 호출 없음 |
| 세로 변경, 이벤트 표시 3줄 유지 | 49 → **0** | 1,715 → **0** | 24.63ms → 호출 없음 |
| 세로 변경, 이벤트 표시 1~4줄 변동 | 53 → **9** | 1,855 → **0** | 25.42ms → **1.437ms** |

표시 용량 변동 시 갱신 P95는 176.304ms → 4.069ms, 갱신 시간 합계는 2,280.21ms → 16.25ms였다. 관리 힙 할당 합계는 19.01MiB → 0.26MiB였고, 새 이벤트 컨트롤은 전체 측정 중 6개만 생성됐다. 이벤트별 리소스 사전 생성은 0회다.

가로/동일 용량 변경의 0회는 **컨트롤 자체의 재구성 경로를 실행하지 않았다는 의미**다. XAML 자동 레이아웃·화면 출력 비용이나 전체 앱 할당이 0이라는 뜻이 아니다. 실제 FPS 및 Outlook 대비 배수는 측정하지 않았다. 용량 경계 갱신은 표본 9개이며, 임시 계측의 범위와 한계는 아래 실행 측정 설명과 동일하다.

원자료는 `artifacts/resize-optimization-20261029/results.json`과 `render-samples.ndjson`, 재현 계측은 같은 폴더의 `instrument.ps1` / `measure-resize.ps1`에 보관했다. 성능 측정 이후 요일 헤더의 구분선과 테마 브러시 갱신을 보완했다. 이 보완은 리사이즈의 재구성 여부를 바꾸지 않으며, 최종 비계측 앱의 아래 회귀 검증에서 확인했다. 계측 코드는 제품 소스와 최종 패키지에서 제거했다.

검증:

- Release x64 예제 빌드: 경고 0 / 오류 0.
- 기존 UI 22개 시나리오 통과: `artifacts/resize-optimization-20261029/ui/results.json`.
- 최종 비계측 앱의 리사이즈·포커스·선택·넘침·원본 변경·Light/Dark/Light·방향키 7개 시나리오 통과: `artifacts/resize-optimization-20261029/resize-ui/results.json`. `scripts/verify-resize.ps1`로 재현한다. 5개 PNG에서 헤더/셀 구분선, 작은 창 더보기, 선택선, 테마 복귀를 시각 검토했다.
- 로컬 NuGet를 새 캐시의 ProjectReference 없는 소비 앱에서 검증한다. 패키지 소비 결과는 `docs/implementation-status.md`에 기록한다.

대량 데이터의 변경 병합·항목별 투영 재사용·구독 차분 처리는 2026-11-01 [API usability improvements](api-usability-improvements.md)에서 반영했다. 1,000개 일괄 추가와 단일 항목 변경의 어댑터 호출 횟수를 실제 소비 앱에서 검증했으며 새로운 시간/FPS 수치를 측정한 것은 아니다. 용량과 무관한 정렬/기간 배치 캐시와 월 이동 시 주 행 재사용은 후속 과제다. 아래 리사이즈 수치는 기존 측정 결과다.

## 결론

최적화 전에는 기능 수보다 **크기 변경마다 UI 전체를 폐기하고 재생성하는 구조**가 병목이었다. 날짜 계산·이벤트 배치 알고리즘보다 기존 UI 객체를 유지하고 변경 원인에 맞는 부분만 갱신하는 작업을 우선했다.

최적화 전 `Calendar.WinUI/Controls/Calendar.cs`의 경로와 당시 행 번호:

1. 46행: 모든 `SizeChanged`에서 `QueueRender()` 호출.
2. 232~244행: 월간 그리드와 이벤트 배치를 다시 계산하고 `_root.Children.Clear()` 실행.
3. 요일 헤더, 날짜 버튼 35/42개, 주별 Grid, 이벤트·더보기, 선택선과 입력 핸들러를 모두 새로 생성.
4. 332행: 선택 가능한 이벤트 조각마다 새 `ResourceDictionary`와 XAML Source 지정.
5. 382~383행: 모든 날짜와 이벤트의 스타일·내용을 다시 설정하고 포커스 복구.

당시 `QueueRender()`는 대기 중인 호출을 합칠 뿐이었다. 연속 리사이즈 중 처리되는 각 호출은 전체 재생성이었고 가로 폭만 변해도 같은 작업을 했다.

## 실행 측정

- Windows 11 빌드 26200, Ryzen 5 5600, x64. SDK 10.0.403, Windows App SDK 2.6.4.
- 예제의 기본 2026년 10월, 5주·35개 날짜 셀, 원본 이벤트 14개, 기본 템플릿.
- Release JIT, `PublishTrimmed=false`, `PublishReadyToRun=false`. 디버거 없이 실행.
- 워밍업 후 각 시나리오에서 `SetWindowPos` 크기 변경을 90회 요청했다. 요청 사이 대기는 16ms이며 실제 간격은 동기 창 크기 처리 비용 등에 따라 길어진다. 아래는 마지막 측정 실행 결과다.

| 시나리오 | 실제 Render 호출 | Render 중앙값 | Render P95 | 날짜 버튼 생성 | 관리 힙 할당 합계 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 가로만 변경, 이벤트 표시 3줄 유지 | 54 | 24.81ms | 197.51ms | 1,890개 | 20.05MiB |
| 세로 변경, 이벤트 표시 3줄 유지 | 49 | 24.63ms | 124.69ms | 1,715개 | 17.95MiB |
| 세로 변경, 이벤트 표시 1~4줄 변동 | 53 | 25.42ms | 176.30ms | 1,855개 | 19.01MiB |

가로만 바꾸는 측정에서 `Render()` 합계는 2,381.17ms였지만 `MonthLayoutEngine.Build()` 합계는 **1.317ms, 약 0.055%**였다. 이벤트 리소스 사전 생성·Source 지정 경로는 270회 실행됐다. 실제 디스크 읽기·XAML 파싱 횟수를 개별 추적한 수치는 아니다. 표시 줄 수가 바뀌지 않아도 같은 재생성 비용이 발생함을 확인했다.

주의할 측정 범위:

- `Render()`는 이 컨트롤의 UI 구성 메서드 이름이다. 뒤에서 실행되는 XAML Measure/Arrange, 렌더링·합성까지 포함한 전체 프레임 시간이 아니다. 따라서 위 숫자를 FPS로 환산하면 안 된다.
- 관리 힙 할당은 `GC.GetAllocatedBytesForCurrentThread()` 차이다. 네이티브 XAML 객체 메모리, GPU 메모리, 다른 스레드는 제외한다. 일시적인 할당 합계이며 메모리 누수 판정이 아니다.
- 진단용 시간·할당 계측과 호출별 로그가 들어간 실행이다. 기록 I/O는 해당 호출의 Render 시간 측정 이후지만 전체 실행에는 영향을 준다. 다른 앱 및 OS 부하를 완전히 통제하지 않았으므로 절대 수치보다 반복 재생성과 계산/UI 비용 비중에 의미가 있다.
- Outlook을 동일 조건에서 측정하지 않았다. 이번 수치는 두 제품의 상대 성능 배수가 아니다.

원자료: `artifacts/resize-investigation-20261029/results.json`, `render-samples.ndjson`, `environment.json`. 재현용 크기 변경 스크립트는 `measure-resize.ps1`, 계측 소스는 `Calendar.instrumented.cs.txt`다. 스크립트는 해당 계측 빌드의 PID를 받아 실행한다. 계측은 제품 소스에서 제거했고 조사 전 SHA256과 일치함을 확인했다.

## 적용 순서

### P0: UI 수명과 크기 변경을 분리

- 요일 헤더·날짜 셀·주별 Grid를 유지한다. 가로 폭 변경은 기존 Star 열과 행의 자동 레이아웃에 맡긴다.
- 세로 높이는 마지막 이벤트 표시 줄 수와 비교한다. 줄 수가 같으면 자체 재배치·UI 생성 작업을 생략한다.
- 줄 수가 변하면 이벤트 영역의 행, 표시/숨김, 더보기 내용만 변경한다. 날짜 셀과 요일 헤더는 유지한다.
- 월·첫 요일 변경 시 날짜 컨텍스트를 교체하고, 5주/6주 전환 시 필요한 주 행만 추가·제거한다. 최소한 리사이즈 경로에서는 이 재구성 경로에 진입하지 않게 한다.
- 렌더 무효화 원인을 범위/데이터/템플릿/표시 용량/선택으로 구분한다. 한 디스패처 갱신에서 최신 변경을 합쳐 처리한다. 추가 프레임 병합은 재측정 후 필요할 때 도입한다.

핵심은 화면 전체의 재생성 없이 기존 요소를 재사용하는 것이다. WinUI의 retained-mode 모델과도 맞는다. [Microsoft WinUI 성능 가이드](https://learn.microsoft.com/en-us/windows/apps/develop/performance/winui-perf)

### P1: 반복 리소스 생성과 전체 선택 갱신 제거

- 현재 이벤트 버튼은 자체 ControlTemplate을 사용한다. 호버·누름 색을 캘린더 전용 ThemeResource 키로 정의하고 템플릿에서 직접 참조해 이벤트마다 생성하는 리소스 사전을 제거한다. Light/Dark/HighContrast 정책은 유지한다.
- 같은 ResourceDictionary 객체를 여러 버튼에 붙이는 방식은 사용하지 않는다. 소유권 문제를 피하고 공통 테마 자원을 컨트롤의 올바른 범위에 한 번 정의한다.
- 날짜 선택은 이전/새 날짜의 컨텍스트·선택선·자동화 상태만 갱신한다. 현재 `RefreshDateStyles()`는 선택할 때마다 35/42개의 새 날짜 컨텍스트를 만든다. 스타일과 날짜 텍스트는 관련 정보가 바뀔 때만 설정한다.
- 이벤트 선택도 이전/새 이벤트의 모든 표시 조각만 갱신한다. 키보드 Tab 대상은 이전/새 날짜만 변경한다.
- 기간 이벤트 조각과 더보기는 안정적인 키로 재사용한다. 입력 핸들러는 최초 생성 시 한 번 연결하고 최신 컨텍스트를 읽게 해 오래된 데이터 캡처를 방지한다.

반복되는 XAML 로딩과 객체 수를 줄이는 방향은 [Microsoft XAML 로딩 최적화](https://learn.microsoft.com/en-us/windows/apps/develop/performance/optimize-xaml-loading)와 일치한다. 개별 리소스 개선 효과는 별도 A/B 측정이 필요하다.

### P2: 데이터 갱신과 배치 캐시

- `CollectionChanged` / 항목 속성 변경마다 전체 원본을 투영하고 구독을 전부 해제·재연결하는 경로를 개선한다. 연속 추가는 한 번으로 병합하고 변경 항목만 투영한다. 지금은 Render만 합쳐지고 데이터 재투영은 매번 실행된다.
- 표시 월·첫 요일에 따른 날짜 범위와 정렬·기간 조각을 캐시한다. 이벤트 데이터/시간대/표시 범위가 그대로면 표시 용량 변경 때문에 정렬과 기간 계산을 반복하지 않는다.
- `PrimaryRange` / `VisibleRange` 조회 때마다 `CreateGrid()`를 수행하는 중복 할당을 줄인다.
- 반복되는 셀의 외곽 구분선용 Border 등은 Grid 자체 테두리로 통합 가능한지 검토한다. 선택선의 독립 레이어와 기존 외곽선 정책은 유지한다. [Microsoft XAML 레이아웃 최적화](https://learn.microsoft.com/en-us/windows/apps/develop/performance/optimize-xaml-layout)

캐시와 변경 알림의 공통 부분은 날짜 범위·이벤트 버전·시간대 기준으로 설계하고, 월간 행/레인 캐시는 월간 뷰 내부에 둔다. 향후 일간·주간에 월간 타입이 전파되지 않게 한다.

## 완료 판정

1. 가로 리사이즈와 동일 표시 용량의 세로 리사이즈에서 컨트롤 자체의 날짜/이벤트 UI 생성 횟수, 이벤트 배치 계산 횟수 모두 0.
2. 표시 용량 경계를 넘을 때에도 날짜 셀 인스턴스 유지. 기간 이벤트 이어짐·정렬·넘침 수와 더보기 전체 목록 유지.
3. 날짜 선택 시 변경 대상은 이전/새 날짜. 이벤트 선택 시 모든 해당 조각의 선택선 유지. 포커스·포인터 입력 상태가 리사이즈 때문에 초기화되지 않음.
4. 5/6주 전환, 인접 월, 날짜/이벤트 선택 OFF, 사용자 템플릿, Light/Dark, RTL, DPI 변경을 회귀 검증.
5. 동일 크기 변경 시나리오를 다시 측정하고 생성/할당 감소를 비교. WPR/WPA의 CPU·XAML Frame Analysis로 실제 UI 프레임과 Measure/Arrange까지 확인. 60Hz 환경에서는 전체 프레임의 16.7ms 예산을 목표로 하되, 이번 Render 수치와 전체 프레임 수치를 혼용하지 않음.
